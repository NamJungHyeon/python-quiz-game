## 항목 2. 코드 구조 및 설계

### Q1. `Quiz`와 `QuizGame` 등 클래스들의 책임을 어떻게 나눴는지 설명할 수 있는가?

**A.** 두 클래스를 "문제 하나를 아는 것"과 "게임 전체를 진행하는 것"으로 역할을 나눴습니다.

- `Quiz`(`quiz.py`)는 문제 1개를 표현하는 클래스로, 자기 자신의 질문·선택지·정답·힌트만 알고
  있습니다. 스스로를 화면에 출력하고(`display`), 정답을 맞았는지 확인하고(`is_correct`), 힌트를
  보여주고(`show_hint`), 딕셔너리로 직렬화/복원(`to_dict`/`from_dict`)하는 것까지만 책임집니다.
  게임이 몇 문제인지, 점수가 몇 점인지는 전혀 모릅니다.
- `QuizGame`(`quiz_game.py`)은 메뉴 출력, 입력 검증, 몇 문제를 뽑아서 진행할지, 점수 계산, 파일
  저장/불러오기 같은 "게임 전체 흐름"을 책임집니다. `Quiz` 객체들을 리스트(`self.quizzes`)로 갖고
  있으면서 필요할 때마다 `Quiz`의 메서드를 호출해서 사용합니다.

한 문장으로 요약하면, `Quiz`는 데이터+자기 자신에 대한 동작, `QuizGame`은 그 데이터들을 모아서
진행하는 흐름 제어를 담당하도록 나눴습니다.

### Q2. "입력 처리(검증)", "게임 진행", "데이터 저장/불러오기" 로직을 어떤 기준으로 분리했는지 설명할 수 있는가?

**A.** `quiz_game.py` 안에서 메서드 이름과 접두사(`_`)로 구분했습니다.

- **입력 처리**: `_get_int_input(prompt, min_value, max_value)`, `_get_text_input(prompt)`,
  `_get_optional_text_input(prompt)`처럼 밑줄로 시작하는 프라이빗 헬퍼 메서드로 모았습니다.
  숫자/텍스트 입력에서 반복되는 검증 로직(공백 제거, 형식 검사, 범위 검사, 빈 입력 처리)을
  한 곳에 모아두고, 다른 기능 메서드들은 이 헬퍼를 호출만 하도록 했습니다. 예를 들어 메뉴 선택도
  `_get_int_input(1, 6)`, 정답 입력도 `_get_int_input(0, 4)`처럼 같은 함수를 재사용합니다.
- **게임 진행**: `play_quiz()` / `_play_single_quiz()`, `add_quiz()`, `list_quizzes()`,
  `delete_quiz()`, `show_best_score()`처럼 메뉴 번호와 1:1로 대응하는 "기능 단위" 메서드로
  나눴습니다. 각 메서드는 입력 검증은 헬퍼에 위임하고, 자신은 그 기능의 흐름(예: 퀴즈 뽑기 →
  출제 → 채점 → 결과 출력)만 담당합니다.
- **데이터 저장/불러오기**: `load_state()` / `save_state()` 두 메서드로 완전히 분리했습니다.
  다른 메서드들은 `self.quizzes`, `self.best_score`, `self.history` 같은 메모리 상의 상태만
  변경하고, 실제 파일 읽기/쓰기는 이 두 메서드만 담당합니다. 이렇게 하면 "언제 저장할지"를
  결정하는 지점(퀴즈 추가 후, 삭제 후, 게임 종료 후)만 관리하면 되고 파일 I/O 코드가 여기저기
  중복되지 않습니다.

즉 기준은 "이 코드가 값을 검증하는가 / 게임 로직을 진행하는가 / 디스크에 접근하는가"였습니다.

### Q3. `state.json` 읽기/쓰기 흐름이 프로그램의 어디에서, 어떤 순서로 발생하는지 설명할 수 있는가?

**A.**

1. `main.py`가 `QuizGame()`을 생성하면 `__init__`에서 바로 `load_state()`를 호출합니다.
   - `state.json`이 없으면(첫 실행) `data.py`의 기본 퀴즈로 시작합니다.
   - 파일이 있으면 JSON을 읽어 `Quiz.from_dict()`로 퀴즈 객체 리스트를 복원하고, `best_score`,
     `history`도 함께 불러옵니다.
   - 이 과정에서 `json.JSONDecodeError`, `KeyError`, `TypeError`, `OSError`가 나면(파일이
     손상됐거나 형식이 다르면) 안내 메시지를 찍고 기본 데이터로 초기화합니다.
2. 그 다음 `run()`이 메뉴 루프를 도는데, **상태를 바꾸는 동작(퀴즈 추가, 삭제, 풀이 완료, 종료)마다
   그 즉시 `save_state()`를 호출**합니다. 즉 "메모리에서 다 끝난 뒤 마지막에 한 번 저장"하는 게
   아니라, 상태가 바뀌는 시점마다 바로바로 파일에 반영해서 프로그램이 예기치 않게 죽어도 직전
   상태까지는 남도록 했습니다.
3. `save_state()`는 `self.quizzes`를 다시 `to_dict()`로 직렬화하고, `best_score`, `history`와
   함께 딕셔너리로 묶어서 `json.dump(..., ensure_ascii=False, indent=2)`로 UTF-8 파일에 씁니다.
   쓰기 중 `OSError`가 나면(디스크 문제 등) 에러 메시지만 출력하고 프로그램은 계속 진행합니다.

### Q4. `Ctrl+C` 또는 `EOF` 상황에서 "안전 종료"를 위해 어떤 처리를 했는지 설명할 수 있는가?

**A.** 두 상황을 다른 위치에서 잡습니다.

- **`Ctrl+C`(`KeyboardInterrupt`)**: `main.py`의 최상위에서 `try: game.run() except
  KeyboardInterrupt`로 잡습니다. 게임 루프 중 어디서 눌리든 결국 이 최상위로 예외가 전파되므로,
  한 곳에서만 처리하면 됩니다. 잡히면 안내 메시지를 출력하고 `game.save_state()`를 호출해 현재까지
  진행된 상태를 저장한 뒤 프로그램을 종료합니다.
- **`EOFError`(입력 스트림이 갑자기 끊기는 경우, 예: 파이프 입력이 끝남)**: 입력을 받는 모든
  헬퍼(`_get_int_input`, `_get_text_input`, `_get_optional_text_input`) 안에서 `input()`을
  `try/except EOFError`로 감싸고, 걸리면 공통 메서드 `_handle_eof()`를 호출합니다.
  `_handle_eof()`는 안내 메시지 출력 → `save_state()` → `raise SystemExit(0)` 순으로 동작해서,
  입력 위치가 어디였든 항상 저장 후 정상 종료(exit code 0)로 이어지도록 했습니다.

두 경우 모두 "저장 먼저, 종료는 그 다음"이라는 원칙을 지켰습니다.

### Q5. 커밋을 어떤 단위로 나누었고, 커밋 메시지 규칙을 어떻게 정했는지 설명할 수 있는가?

**A.** 기능 하나가 "동작 가능한 상태"가 될 때마다 커밋했습니다. 예를 들어 메뉴 골격 완성,
`Quiz` 클래스 완성, 기본 데이터 추가, 퀴즈 풀기 기능 완성처럼 눈으로 확인 가능한 단위로 쪼갰고,
한 커밋 안에 여러 기능을 섞지 않으려고 했습니다.

메시지는 `타입: 내용` 형식을 따랐습니다.

- `Feat:` — 새 기능 추가 (예: `Feat: 퀴즈 풀기 기능 구현 (QuizGame 클래스, 채점 및 결과 출력)`)
- `Refactor:` — 동작은 그대로 두고 구조/처리 방식 개선 (예: `Refactor: EOFError/KeyboardInterrupt
  예외 처리 강화`)
- `Docs:` — 문서 변경 (예: `Docs: README 작성`)
- `Chore:` — 설정 등 자잘한 초기 작업 (예: `Chore: 프로젝트 초기 설정`)

"수정", "업데이트"처럼 무엇을 했는지 알 수 없는 형식적인 메시지 대신, 괄호 등으로 구체적으로
무엇을 구현했는지 덧붙였습니다.

## 항목 3. 핵심 기술 원리 적용

### Q1. 클래스를 사용한 이유는 무엇이며, 함수만으로 구현할 때와 어떤 차이가 있는지 설명할 수 있는가?

**A.** 퀴즈는 "문제, 선택지, 정답, 힌트"라는 데이터와 "출력한다, 채점한다"는 동작이 항상 함께
움직입니다. 함수만으로 만들면 이 데이터들을 딕셔너리나 여러 개의 리스트(문제 리스트, 정답
리스트...)로 따로 들고 다니면서, 함수마다 매번 "몇 번째 문제인지" 인덱스를 넘겨줘야 합니다.
퀴즈가 6개면 괜찮지만, 필드가 늘어나거나(예: 난이도 추가) 퀴즈 개수가 많아지면 인덱스가 꼬이기
쉽고, 데이터와 그 데이터를 다루는 함수가 코드 상에서 멀리 떨어져 있어 관리가 어려워집니다.

클래스로 만들면 `quiz.is_correct(answer)`처럼 "이 퀴즈에게 직접 물어보는" 형태가 되어 어떤
퀴즈의 정답인지 헷갈릴 여지가 없고, 문제 하나에 관련된 데이터와 동작이 한 덩어리로 묶여서 관리
포인트가 명확해집니다. 또한 `QuizGame`도 클래스로 만들어서 `self.quizzes`, `self.best_score`
같은 "게임 상태"를 인스턴스가 스스로 들고 있게 했는데, 이렇게 하면 전역 변수를 여러 함수가
공유하며 값을 바꾸는 구조를 피할 수 있습니다.

### Q2. JSON 파일로 데이터를 저장하는 이유와 JSON 형식의 특징을 설명할 수 있는가?

**A.** 이 프로젝트의 데이터(퀴즈 목록, 최고 점수, 게임 기록)는 리스트와 딕셔너리가 중첩된
구조입니다. JSON은 Python의 `list`/`dict`/`str`/`int`/`bool`/`None`과 거의 1:1로 대응되기 때문에
`json.dump()` / `json.load()` 한 줄로 파이썬 객체를 그대로 파일로 저장하고 복원할 수 있습니다.
텍스트 기반이라 사람이 파일을 직접 열어서 읽고 검증하기도 쉽고, 별도의 외부 라이브러리 없이
Python 표준 라이브러리(`json` 모듈)만으로 다룰 수 있다는 점도 이 과제의 제약(표준 라이브러리만
사용)과 맞았습니다. CSV였다면 `quizzes`처럼 리스트 안에 리스트(선택지 4개)가 중첩된 구조를 표현하기
번거로웠을 것입니다.

### Q3. 파일 입출력에서 `try/except`가 필요한 이유(발생 가능한 실패 케이스 포함)를 설명할 수 있는가?

**A.** 파일 입출력은 프로그램 로직만으로는 통제할 수 없는 외부 요인에 의해 실패할 수 있기
때문입니다. 이 프로젝트에서 실제로 처리한 케이스는:

- **읽기(`load_state`)**: 파일이 존재하지 않음(최초 실행) → `os.path.exists`로 먼저 분기.
  파일은 있지만 JSON 문법이 깨졌음 → `json.JSONDecodeError`. 스키마가 예상과 다름(`quizzes` 키가
  없거나 항목 구조가 다름) → `KeyError`/`TypeError`. 권한 문제 등으로 파일을 못 여는 경우 →
  `OSError`. 이 네 가지를 한 번에 잡아서 안내 메시지를 띄우고 기본 퀴즈 데이터로 초기화합니다.
- **쓰기(`save_state`)**: 디스크 공간 부족, 권한 문제 등으로 쓰기가 실패할 수 있는 `OSError`를
  잡아서 에러 메시지만 출력하고 프로그램이 죽지 않도록 했습니다.

`try/except` 없이 그냥 열고 읽으면, 파일이 하나라도 깨진 순간 프로그램이 예외를 던지고 즉시
종료돼버립니다. 사용자 입장에서는 실행할 때마다 파일이 깨질 수 있는데, 그때마다 프로그램이
죽어버리면 "기본 데이터로라도 계속 쓸 수 있어야 한다"는 요구사항을 만족할 수 없기 때문에
`try/except`로 감싸고 복구 경로를 만들어야 했습니다.

### Q4. 브랜치를 분리해 작업한 이유와 병합(merge)의 의미를 설명할 수 있는가?

**A.** 퀴즈 풀기 기능은 `Quiz`/`QuizGame` 두 클래스와 채점 로직까지 얽혀 있어서 한 번에 완성되지
않는 작업이었습니다. `main` 브랜치에서 바로 작업하면, 기능이 완성되기 전 중간 상태의 커밋들이
`main`에 그대로 남아 "언제든 실행 가능한 상태"라는 `main`의 안정성이 깨집니다. 그래서
`feature/quiz-play`라는 별도 브랜치를 만들어(`git checkout -b feature/quiz-play`) 그 안에서
기능을 완성한 뒤, 다 되고 나서야 `git merge feature/quiz-play`로 `main`에 합쳤습니다
(커밋 `45768ca`).

병합(merge)은 두 브랜치의 커밋 히스토리를 하나로 합치는 작업입니다. `main`은 그동안 다른 변경이
없었기 때문에 이 경우엔 단순히 `feature/quiz-play`의 커밋들을 `main` 위에 이어 붙이는 형태의
병합이 이뤄졌고, 병합 커밋(`45768ca`)이 두 브랜치가 합쳐진 지점을 표시합니다.

### Q5. `state.json` 데이터 구조(필드/중첩 구조)를 현재 형태로 설계한 이유를 설명할 수 있는가?

**A.** 최상위를 `quizzes` / `best_score` / `history` 세 개의 키로 나눈 이유는, 이 세 가지가
서로 다른 생명주기를 가진 데이터이기 때문입니다.

- `quizzes`는 사용자가 추가/삭제할 때마다 바뀌는 "퀴즈 원본 데이터"이고, 리스트 형태로 각 항목이
  `Quiz.to_dict()`의 결과(`question`, `choices`, `answer`, `hint`)와 정확히 대응하도록 해서,
  불러올 때 `Quiz.from_dict()`로 그대로 복원할 수 있게 맞췄습니다.
- `best_score`는 "지금까지의 최고 기록" 단 하나만 있으면 되므로 리스트가 아니라 객체(딕셔너리)
  하나로 두었고, 아직 한 번도 안 풀었을 때를 표현하기 위해 `null`을 허용하도록 설계했습니다.
- `history`는 풀 때마다 계속 쌓이는 로그성 데이터라서 리스트로 두고 뒤에 계속 추가(`append`)만
  하는 구조로 만들었습니다. `best_score`와 필드가 겹치지만(`score`, `correct`, `total`) 성격이
  다르기 때문에(하나는 "최고 기록 1개", 하나는 "매 회차 기록 전체") 굳이 하나로 합치지 않고
  분리했습니다.

즉 "값 하나만 필요한 데이터(`best_score`)"와 "계속 쌓이는 데이터(`history`)", "목록 자체가
사용자에 의해 변하는 데이터(`quizzes`)"를 성격별로 나눈 것이 설계 기준입니다.

## 항목 4. 심층 인터뷰

### Q1. 퀴즈 데이터가 1000개 이상으로 늘어난다면 현재 JSON 저장 방식에 어떤 한계가 생길 수 있는지 설명할 수 있는가?

**A.** 지금 방식은 퀴즈 하나를 추가하거나 삭제할 때마다 `self.quizzes` 전체를 다시
`to_dict()`로 직렬화해서 `state.json` 파일 전체를 통째로 다시 씁니다(`save_state()`). 문제가
1000개, 10000개로 늘어나면:

- **쓰기 비용 증가**: 문제 하나만 바꿔도 파일 전체를 매번 다시 쓰기 때문에, 데이터가 커질수록
  저장(퀴즈 추가/삭제/게임 종료마다 호출)이 점점 느려집니다.
- **메모리 사용량**: `load_state()`가 실행 시작할 때 파일 전체를 한 번에 메모리로 읽어들이므로,
  데이터가 아주 커지면 프로그램 시작 시간과 메모리 사용량이 함께 늘어납니다.
- **동시성 문제**: 여러 프로세스가 동시에 같은 `state.json`을 쓰려고 하면(지금 구조는 이를
  전혀 고려하지 않음) 서로 덮어써서 데이터가 유실될 수 있습니다.
- **검색/필터링의 비효율**: "특정 주제의 퀴즈만 보기"처럼 조건 조회가 필요해지면, 지금은 매번
  파이썬 리스트를 전체 순회해야 합니다.

이 정도 규모라면 SQLite 같은 파일 기반 DB나 실제 RDBMS로 옮겨서, 필요한 레코드만 읽고/쓰고
인덱스로 검색하는 방식이 더 적합합니다. 다만 지금 과제 규모(퀴즈 수십 개, 개인용 콘솔 프로그램)
에서는 JSON 방식이 구현이 단순하고 파일 하나로 데이터를 옮기기도 쉬워서 적절한 선택이라고
생각합니다.

### Q2. `state.json`이 손상되어 JSON 파싱에 실패한다면, 사용자가 데이터를 잃지 않도록 어떤 대응이 가능한지 설명할 수 있는가?

**A.** **지금 구현**은 `load_state()`에서 `json.JSONDecodeError` 등을 잡으면 안내 메시지를
출력하고 기본 퀴즈 데이터로 초기화합니다 — 프로그램이 죽지 않고 계속 쓸 수는 있지만, 손상되기
직전까지 쌓여있던 사용자의 퀴즈/점수/기록은 그 시점에 사라집니다.

데이터를 잃지 않으려면 추가로 이런 방법을 적용할 수 있습니다.

- **쓰기 시 원자적 교체(atomic write)**: `state.json`에 바로 쓰지 않고 `state.json.tmp`에 먼저
  쓴 뒤 `os.replace()`로 원래 파일명으로 교체합니다. 쓰는 도중 프로그램이 죽거나 정전이 나도
  기존 `state.json`은 온전히 남아있으므로, 애초에 "쓰다 만 파일 때문에 파싱이 실패하는" 상황
  자체를 줄일 수 있습니다.
- **백업 파일 유지**: 저장할 때마다 `state.json`을 `state.json.bak`으로 먼저 복사해두고, 읽기에
  실패하면 기본 데이터로 가기 전에 `.bak` 파일로 복구를 먼저 시도합니다.
- **손상된 원본 보존**: 파싱에 실패한 `state.json`을 삭제/덮어쓰기 전에
  `state.json.corrupted.<timestamp>` 같은 이름으로 남겨두면, 나중에 수동으로라도 복구를
  시도해볼 여지가 생깁니다.

세 가지 중 실무에서 가장 먼저 적용하는 건 원자적 쓰기(첫 번째)입니다. 애초에 파일이 손상될
확률 자체를 줄여주기 때문입니다.

### Q3. "정답 채점 방식(점수 계산)"이나 "퀴즈 구조(선택지 개수 등)" 요구사항이 바뀐다면, 어떤 파일/클래스/메서드를 먼저 수정해야 하는지 설명할 수 있는가?

**A.** 두 경우를 나눠서 설명하면:

- **점수 계산 방식이 바뀌는 경우** (예: 정답률 기반이 아니라 문제당 고정 점수 + 시간 보너스로
  변경): `quiz_game.py`의 `play_quiz()` 안에서 `raw_score`, `score`를 계산하는 부분과, 클래스
  상수 `HINT_PENALTY`만 수정하면 됩니다. `Quiz` 클래스나 `state.json` 스키마는 건드릴 필요가
  없습니다 — 점수 계산은 전적으로 `QuizGame`의 책임이기 때문입니다. 다만 계산에 필요한 새 정보
  (예: "문제 풀이 소요 시간")가 필요하다면 `_play_single_quiz()`에서 그 정보를 추가로 수집해서
  넘겨줘야 하고, `history`에 새 필드를 추가해야 할 수도 있습니다.
- **퀴즈 구조가 바뀌는 경우** (예: 선택지를 4개에서 5개로, 또는 객관식이 아니라 단답형으로 변경):
  `Quiz` 클래스(`quiz.py`)의 `__init__`, `display()`, `is_correct()`, `to_dict()`/`from_dict()`가
  먼저 수정 대상입니다. 이어서 `QuizGame.add_quiz()`에서 선택지를 입력받는 반복문(`for i in
  range(1, 5)` 부분)과 정답 번호 범위 검증(`_get_int_input("정답 번호 (1-4): ", 1, 4)`)도 그
  구조에 맞게 고쳐야 합니다. `data.py`의 기본 퀴즈 데이터도 새 구조에 맞게 다시 작성해야 하고,
  기존 `state.json`을 읽을 때 예전 스키마와 호환되지 않을 수 있으므로 `load_state()`에 마이그레이션
  로직(또는 최소한 스키마 버전 체크)을 추가하는 것이 안전합니다.

정리하면, **"몇 점을 줄지"는 `QuizGame`(정확히는 `play_quiz`) 책임**이고, **"문제가 어떤
모양인지"는 `Quiz` 책임**이라는 클래스 분리 원칙을 그대로 따라가면 수정 범위를 좁힐 수 있습니다.
